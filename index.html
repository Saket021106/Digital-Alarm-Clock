Why an RTL Alarm Clock?

A digital clock looks simple, but it is a compact tour of real digital design: a time base, a control state machine, data registers with arithmetic, user input handling, and an output display. Every one of these appears in larger embedded and FPGA systems.

This project implements a complete alarm clock at register-transfer level. The user types four digits on a keypad, presses a button to commit them as either the current time or the alarm time, and the clock then counts minutes in BCD with correct 24-hour rollover. When the current time matches the alarm on all four digits, sound_alarm goes high.

Modular

Each block has one responsibility, so the datapath holds no decision logic and the FSM does no arithmetic.

Shared keypad

The same four typed digits become the time or the alarm, depending on which button the user presses.

Testable

A fast_watch input makes a simulated minute pass every simulated second for quick verification.

Architecture Principles

Separate control from data

The controller FSM generates every control signal (load_new_c, load_new_a, show_a, show_new_time, shift, reset_count). The counter, alarm register, key buffer and display only react to those signals. This split keeps each block small enough to verify on its own.

Moore state machine

All FSM outputs depend on the current state only, not on inputs. Outputs therefore cannot glitch when a button or key changes mid-cycle, and each output is easy to trace on a waveform.

BCD storage

Time is kept as four BCD digits (ms_hr, ls_hr, ms_min, ls_min). No binary-to-decimal converter is needed, and the display converts a digit to ASCII by adding 0x30.

Single free-running time base

One 14-bit counter derives both one_second and one_minute. With fast_watch high, one_minute follows one_second, so no other module needs a test mode.

Sentinel-coded keypad

key == 4'd10 means "no key pressed", and values 0 to 9 are digits. This uses a spare 4-bit code instead of an extra valid line.

From Specification to Verified RTL

  1. Specify behaviour. 24-hour time, keypad entry of four digits, a commit button for time and one for alarm, alarm-display-while-held, and a 10-second entry timeout.
  2. Partition the system. Split into time generator, controller, key register, current-time counter, alarm register and display, and define the control signals that connect them (see the block diagram).
  3. Design the FSM. Seven states covering idle, alarm view, key storing, waiting, entry and the two commit states. Choose Moore outputs.
  4. Write the RTL. One SystemVerilog file per block, integrated by the top module alarm_clk_rtl.
  5. Build a task-based testbench. Reusable tasks (press_key, enter_digits, pulse_time_button, pulse_alarm_button) drive four directed tests.
  6. Simulate and inspect the waveform. Check FSM state, shift-register contents, register loads, display characters and sound_alarm.
  7. Document the results. Capture the block diagram and annotated waveform, and record measured synthesis figures once available.

System Connectivity

The diagram shows the clock and reset feeding every block, the buttons and keypad entering the controller, and the control signals fanning out to the datapath. The four-digit key buffer connects to both the counter and the alarm register, and the display driver receives current time, alarm time and key buffer together with the show_* flags.

Alarm controller

Inputs: clk, reset, one_second, alarm_button, time_button, key. Outputs: reset_count, load_new_c, show_new_time, show_a, load_new_a, shift.

Datapath

Key register feeds counter and alarm register. Counter and alarm register feed the display driver, which outputs the four display characters and sound_alarm.

What each signal group shows

clk, reset

Reset holds all registers at 0 for 100 ns, so the display starts at "0000" (ASCII 48 in each digit).

key, shift

Each valid key is followed by a return to 10 (no key). shift pulses once per digit, which is what advances the buffer.

state, next_state

Repeating 3, 4, 2 per key, then 6 on commit and 0 (SHOW_TIME) after it. next_state leads state by one edge, as expected for registered state.

key_buffer_*, new_alarm_*, new_current_time_*

These carry the same digits, since the key buffer feeds both registers. They only differ in what the load signals do with them.

display_*

ASCII characters. 48 to 57 map to '0' to '9'. Each digit updates independently as its source changes.

timeout, timeout_cnt

Stay at 0 in this window because the 10-second timeout counts one_second pulses, which occur every 256 clocks and are beyond this view.

How this validates the design

Entry path: digits arrive in MS-hour to LS-minute order and settle in the right buffer positions. Control: every FSM transition matches the specified sequence and the Moore outputs change with state only. Commit: pressing time_button loads the counter and resynchronises the time base in the same cycle. Display: mode selection and ASCII conversion are correct. Alarm compare: sound_alarm depends on a four-digit match.

The testbench itself also prints results for four tests: set time 09:43, set alarm 09:44, run until the minute rolls to 09:44 (expecting sound_alarm = 1), and show the alarm on demand. The waveform above covers the first stages of these; the later tests run past its window.

Timing and Configuration

Time base

Designed for a 256 Hz clock. one_second every 256 clocks gives 1 s. The counter wraps at 15360 = 60 x 256 clocks, giving 1 minute.

Counter width

15360 fits in 14 bits (maximum 16383), so the counter needs 14 flip-flops.

fast_watch

One minute passes per second, or every 256 clocks. In simulation this takes about 5.12 microseconds per minute at a 20 ns clock.

Entry timeout

10 one_second pulses, counted by a 4-bit counter, then a return to SHOW_TIME.

24-hour rollover

Checked explicitly at 23:59 to 00:00. Otherwise ls_min carries to ms_min at 9, and minutes carry to hours at :59.
